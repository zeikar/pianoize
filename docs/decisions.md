# Design decisions

The decisions in force, each with its reason and, where one was weighed, the alternative it was chosen over. A decision that changes is edited where it stands; git keeps the history. What each command does is in the other pages under `docs/`.

## Direction

- **Falling-notes videos of piano arrangements, the arrangement first.** The videos are for a personal, non-monetized YouTube channel. What makes one worth watching is the arrangement, so the renderer came last, once the arrangements sounded right as MIDI.
- **The milestones** the docs refer to: M0, the rules and the package skeleton; M1, a trial of the audio-to-piano models and melody extractors that run on a Mac; M2, polishing the chosen model's cover; M3, an arrangement an agent writes; M4, the renderer.
- **The CLI never calls an LLM.** An agent session, such as Claude Code, writes a small file into `work/`: chord edits, a correction spec or a score. Code validates it and applies it or builds it deterministically, so the same inputs give byte-identical output. There is no API key and no cost, and every file can be read and edited by hand. A CLI that calls an API could later write the same formats.

### The arrangement starts from tsumugi-piano-cover

M1 ran the audio-to-piano models that run on a Mac and scored each against the original's harmony. tsumugi-piano-cover passed the most checkpoints on the first test song, 11 of 20 against Etude's 10, and to the user's ear its render kept the harmony, so its cover was what the first arrangements started from. That path, `arrange-cover`, now runs when the user asks for it: the defaults read no cover, an instrumental's [the transcription-only arrangement](#the-transcription-only-arrangement) and a sung song's [the vocal arrangement](#the-vocal-arrangement), both from tsumugi's transcription. Etude sounded less clear, and its ShareAlike weights complicate the videos; Pop2Piano has no license ([Models tried and not used](#models-tried-and-not-used)).

The melody comes with it, on every path. tsumugi-piano-cover is conditioned on tsumugi's transcription, whose `melody` track is the melody the arrangement carries, so no separate melody extractor feeds pianoize. GAME and Basic Pitch were compared in M1 only for an arrangement built from scratch; torchcrepe, the fallback, was not needed.

## Harmony

- **chordotomy stays as it is.** [chordotomy](https://github.com/zeikar/chordotomy) gives chords, the bass and inversions, beats, key regions and Roman numerals, and deliberately stops there: melody to MIDI is outside it, so pianoize doesn't add it there. pianoize reads its timeline JSON, checks `schema_version` (11), and runs the `chordotomy` CLI as a separately installed tool. chordotomy's model extra pins torch, lv-chordia and beat-this, and the models pianoize runs bring their own pins, so they don't share an environment.
- **No reading is the answer key.** In M1, scoring tsumugi's cover against chordotomy's timeline counted the analyzer's misreadings as the model's mistakes: it read Cm over E♭ as E♭ major, an augmented chord as major, and a melody note on top of the piano as the chord. Web chord charts often get the harmony right but carry no timing and may be transposed or simplified; tsumugi's transcription brings its own chord, bass and melody tracks. So an agent weighs these readings against each other and against the notes, and writes one refined harmony timeline. That timeline, not chordotomy's, is what the notes are checked against ([Polishing the cover](#polishing-the-cover)).
- **Web chord charts are left out for now.** U-FRET draws its chords with JavaScript, and its terms forbid use outside the service, analysis and heavy load; ChordWiki refuses automated requests. Charts can come back as a chord sequence the user pastes. A chart copied from a website stays in `work/`, like a recording.
- **Scoring a result's harmony.** `pianoize evaluate` renders a result, analyzes it with chordotomy and compares it with the original's timeline at checkpoints, runs of segments such as a borrowed iv or a chromatic bass line, within one beat either way ([the pass rule](evaluation.md#the-pass-rule)). Sevenths and tensions are ignored, because chordotomy's sevenths come and go between repeats of one passage. The bass must match where the original is inverted, because in a passage like C/E – Cm/E♭ – G/D – A/C♯ – D the descending bass is the point. A human cover is scored the same way, as a check of the scoring: its simplifications have to come out as failures.
- **Since M2 the notes are checked directly.** `pianoize harmony-evidence` compares a result's notes with the refined timeline, segment by segment, with no render or reanalysis in between, so the analyzer's misreadings no longer count against a result ([docs/polishing.md](polishing.md#harmony-evidence)). The render-and-analyze scoring stays in `pianoize evaluate`.
- **A song's checkpoints stay in `work/`,** since they are made from its recording. The repository keeps only their format and synthetic examples.

## Licenses

- **Non-commercial weights are usable,** since nothing is monetized. They are never committed: `pianoize setup` installs them once into the user's cache, with their terms shown. Each model's code and weight licenses are checked again before it is used, because they change, and the date and the source are recorded below.
- **A non-commercial model's output is treated as non-commercial.** A weight license binds the use of the model, and the repository holds none of its code or weights, so the repository's own license is unaffected. Whether a model's output counts as material adapted from its weights is unsettled, so a video made from tsumugi-piano-cover's cover stays non-monetized and credits the model ([What goes into a video](#what-goes-into-a-video)). tsumugi's transcriber, with MIT code and weights, carries no such terms; the [transcription-only arrangement](#the-transcription-only-arrangement) owes the cover nothing.
- **No GPL or AGPL code.** The code is published under MIT, so no GPL or AGPL code goes into the repository or its dependencies, Python or npm, vendored, imported or bundled. Neothesia and YourMT3+ are out for this reason. LGPL is allowed, as in chordotomy.
- **A separately installed tool's license doesn't matter.** A tool the user installs and pianoize runs as a subprocess, such as FluidSynth, ffmpeg or Chrome, is not part of what is published. Homebrew's FFmpeg is a GPL build (`--enable-gpl`): tsumugi's torchcodec loads it inside tsumugi's own process, and nothing committed imports or links it.

## What goes into a video

A video carries only the piano pianoize renders, never the original audio or vocals separated from it. Its description credits the song, the artist and the composer; the arrangement model, tsumugi-piano-cover (anime-song, CC BY-NC 4.0), whose license asks for attribution; and the SoundFont, with the line under [MIDI is rendered with FluidSynth](#midi-is-rendered-with-fluidsynth).

Songs under a creator's fan-work guidelines follow them. For a hololive song these are hololive's music guidelines ([hololivepro.com/terms](https://hololivepro.com/terms/), read 2026-10-13): the credit is required, and registering the video with Content ID or any other automatic identification is not allowed. Corporate use, and for-profit use beyond the sharing site's own monetization, is refused; an individual may use the site's partner program, YouTube's ad revenue included. Before uploading, check that the song is not on the guidelines' exclusion list, and its registration with JASRAC or NexTone, whose databases the guidelines point to.

What the video shows is under [Rendering](#rendering).

## Preparing a song

`pianoize setup`, `pianoize prepare` and the `prepare-song` skill make a song's arranging inputs from its recording ([docs/preparing.md](preparing.md)).

- **The models live user-wide.** A plugin user has no `work/`, and the user chose global caches shared with chordotomy. The pianoize home is `$PIANOIZE_HOME`, else `$XDG_CACHE_HOME/pianoize`, else `~/.cache/pianoize`; it holds the two clones, their environments, tsumugi's checkpoints and the stem splitter's weights. The cover's weights go in the Hugging Face hub cache, shared with whatever else uses that model. uv's cache stays global, shared with chordotomy and every other uv project.
- **Setup installs both models, pinned** ([the pins](#models-weights-and-tools-in-use)), **and fetches tsumugi's own checkpoints too,** checking each against its recorded SHA-256; otherwise the first `prepare` would download 850 MB unpinned. Setup streams uv's and huggingface_hub's progress to the terminal.
- **yt-dlp runs through `uvx … @latest`, not as a dependency.** An old yt-dlp stops working when YouTube changes, so every run takes the newest, as chordotomy's skill does.
- **The download** is one video's audio as mp3, since the decoder reads wav, flac, ogg and mp3 but not m4a or webm, with no limit on its length. `--no-playlist -I 1` takes a single video from a link to a playlist or into one, and the `deno` extra brings the JavaScript runtime YouTube needs.
- **The logs** keep the tools' output in order, a line at a time, and leave out the `@@` lines the worker streams to Cover Studio's page.
- **The melody goes through `grid.build`,** keeping only the `melody` track with `source.mid`'s tempo changes and time signatures, so it carries no chord markers and reads on the tempo map the cover is built from.
- **A stopped `prepare` exits 130** and removes its scratch directory.
- **The transcription is kept.** tsumugi's transcriber is not deterministic, so each transcription is one draw: `transcription.mid` is kept and reused rather than made again. The cover is generated with seed 0.

### The steady tempo grid

tsumugi's beat tracker can run at half speed through long stretches of a song and squeeze bars elsewhere, as it did on the second test song. The cover model builds its beat rows from `source.mid`'s tempo map, so the cover's rhythm bends with it. `regrid` repairs only short hiccups in a finished cover; gridding the transcription before the cover is made fixes the cause. The rules and their numbers are in [the tempo grid](preparing.md#the-tempo-grid); the thresholds, the window and the downbeat vote were set from probes on random attacks and on two real transcriptions, the second test song and an instrumental.

- **The grid runs inside `prepare`,** automatically, before the cover, chosen over a separate command or both.
- **One steady tempo or none.** A fit that is not good leaves tsumugi's map as it is. Notes are not quantized: every note keeps its seconds.
- **The raw transcription is `transcription.mid`; `source.mid` is the gridded one.** `source.mid` keeps its name because it is the generator's `--source` and the arranging commands'. `transcription.mid` is read only when `source.mid` has to be made, so a directory from before the grid is reused as it is. Such directories are not migrated, and `regrid` stays for the covers made before the grid, both chosen over rewriting what already works.
- **The drums count as attacks:** they are the best beat evidence. Leaving out the vocal barely moved the fit, so there is no rule for it.
- **The fit is a brute-force search,** with no coarse-to-fine stage: it takes about a second on a 5-minute song.
- **The octave is tsumugi's.** Some anchor is needed, tsumugi's was right over most of both transcriptions, and the attacks can't judge it for eighth-note music: on the second test song a half-tempo grid explains 87% of the attacks against the fit's 89%. So the search keeps to a band around tsumugi's dominant tempo.
- **A map across two octaves grids at the one tsumugi held longer,** and `prepare` warns of the other, chosen over refusing it, which would refuse the second test song, a quarter of it at half speed, and over a silent majority. The warning has no floor: one that hides below a cutoff hides a real wrong octave too. A song tracked at the wrong octave for most of its length grids there; a test pins that limit.
- **A sustained stretch the grid misses refuses the fit,** judged by the attacks' beat period over 10 s spans. A global coverage gate accepted a synthetic song that changes tempo at 80 s. A veto from how long tsumugi's map runs off the fit caught an 80 s change but not a 40 s one, and refused a steady song whose map was distorted for 60 s: duration doesn't say which of the map and the music is right. A first beat test, the share of on-grid attacks on the beats, refused uniform eighths at half the tempo and uniform sixteenths; beat occupancy fills every beat for them.
- **The pickup bar is bar 1 at its own tempo,** then the steady tempo from bar 2: the only way to keep tick 0 at 0 s, every event's seconds, and the bar lines on the downbeats with one meter.
- **The meter is tsumugi's first,** through the song. A later signature with the same bar, the 8/8 tsumugi writes for stretches of a 4/4 song, is no change. One with another bar is dropped, with a line asking to check the bars by ear. tsumugi changes its meter with its tempo map when its beat tracking flips to the other octave mid-song, and the steady grid replaces that map; the score format needs one meter anyway. A real change of meter loses its bar lines after the change, but such a song could not be arranged before either. An n/16 bar is first read as n/4 at four times the bpm, keeping its seconds: tsumugi writes stretches of an instrumental 4/16 at 42.5 bpm between 4/4 bars at 170, the same bars with its beat on the sixteenth, and at 42.5 bpm no fit holds the eighths. Only n/16 is read so: an n/8 bar is the usual notation of a compound meter. tsumugi's chord markers agree with its bar lines but are not used.
- **`regrid.repair` is neither reused nor changed.** It keeps a map except inside its spans, while the grid replaces the whole map.

### Instrumentals

An instrumental has no `melody` track, which stopped `prepare` at the melody step. Now it has no melody by default, and `--melody-track NAME` takes an instrument's track as the melody, chosen over no melody alone and over only making `prepare` finish.

## Polishing the cover

M2's commands polish tsumugi's cover note by note ([docs/polishing.md](polishing.md)). Since M3 this path is kept but is not the main one: an [arrangement an agent writes](#an-agent-writes-the-arrangement) sounded better than the polished cover. Its refined timeline and evidence table remain evidence for that arrangement.

- **Four kinds of problem are worth fixing:** a chord that doesn't match the song, a note that sounds like a slip, a voice that jumps or a bass line that breaks off, and timing that stumbles. An agent can't listen, so code reads the cover's notes and lists candidates of each kind with the notes around them, and the agent judges each against the refined harmony and the music around it.
- **The agent writes two small JSON files; code writes the rest.** The agent writes the chord edits (chords over beat ranges) and the correction spec (a verdict per candidate, an edit per fix, each with a reason). Code validates both and writes the refined timeline and a polished copy of the cover. So what the agent decided stays small enough to read and edit, every change carries a reason, and the same files give the same bytes. The cover itself stays untouched, and each change can be read and undone, as hand edits to its MIDI could not be.
- **The refined timeline is chordotomy's with edited spans,** at `<stem>.refined.chords.json`, so a save in chordotomy's viewer, which writes `<stem>.edited.chords.json`, never overwrites it. It keeps chordotomy's `generator` and `candidates`, and sets `numeral`, `role`, `function` and `target` to `null` on edited segments: pianoize does not port chordotomy's harmonic analysis, and the viewer recomputes them at its first edit. An edit is a beat range, so a chord change between two beats goes to a beat.
- **Melody protection is pitch only.** A cover note that carries the melody never changes pitch; deleting or retiming it stays allowed. It is matched to a note of tsumugi's melody track on the same pitch class at or below it, because the cover mostly plays the melody an octave up.
- **`add` is allowed, and the pedal is ignored.** A missing chord tone may need a new note. The checks count a note from its note-on to its note-off, so a tone only the pedal holds counts as missing; the spec has no pedal edit.
- **The thresholds** were tuned once, on the first test cover, so that no kind floods the judging with more than about 60 candidates. Only `off_grid_ms` moved, from 45 to 50 ms.

## Arranging

### An agent writes the arrangement

An agent following one of the arranging skills, run as a subagent (below), reads tsumugi's transcription of the band and its melody, and the cover where the user asked for the cover's arrangement, and writes a per-bar score for two hands into `work/`, song-specific like a correction spec. pianoize commits only generic, tested tooling: the score format, a build into a two-hand MIDI on the cover's tempo grid, a check of playability and harmony, and a per-bar dump for the agent to read ([docs/arranging.md](arranging.md)).

At M2's listening gate the user compared one excerpt arranged several ways. The one an agent wrote as a per-bar score from tsumugi's cover and vocal transcription was rated best: cleaner than the polished cover, written for two hands and checked as playable, and keeping the song's feel, its rhythmic hits included. Weighed against it were the polished cover; a rule-based arrangement from the melody and the refined chords, cleaner than the cover; the polished cover with a clean melody on top, too ornate, since the cover's right-hand lines were written around its own melody; that rule-based right hand over the cover's left hand; and left hands regenerated from the chords on the cover's rhythm. Committed tooling makes the next song reproducible, where one-off scripts fit one song.

- **The cover's notes may be copied** where they render a moment best, once their strays are cleaned. Since the arrangement copies them in places, the video keeps the cover's credit and non-commercial terms.
- **The melody is tsumugi's `melody` track,** not the cover's top line.
- **The transcription is read in every bar.** The cover blends the band into one piano part, and leaves parts of it out; the transcription keeps a track per instrument. `dump-bars --source --every-bar --drums` prints the drums and each instrument's top line under the cover in every bar. Where no one sings, the right hand takes the line that carries the tune. Under the voice, the agent takes the backing vocal's line, the bass's motion and a pulse the cover only holds, makes the stops and breakdowns follow the drums, and compares the finished score with the band. It was read only where no one sings until a review of the fourth test song against its transcription found chords over the wrong bass, stops and breakdowns that copied bars played through, and a backing vocal and a pulse left out. Without a transcription, the score is written from the cover and the melody.
- **The arranger runs as a subagent.** The arranging skills dispatch the plugin's `arranger` subagent, defined in `agents/arranger.md`, to read the dump, write the score and loop the build and the check; the main session gathers the inputs, relays the arranger's report and the user's answers, and continues the same subagent for revisions. A full song's dump with the band in every bar runs to thousands of lines and the build-check loop adds more, which crowd out the conversation in the main session. A definition rather than a general-purpose agent, because its tools are the shell and the files only, with no web access, so the audio and the song's content stay on the machine; and the skills share one role and one report across revisions. It records the skill and the rule files it was dispatched with at the top of `notes.md`, so a revision in a new conversation is redispatched with the same files, whichever arranging skill the request reached. A session without the type dispatches a general-purpose agent that reads the definition first; that agent has every tool, so there the limit rests on the definition's instructions.
- **The arranging rules are shared files; the skills are thin.** The rules live in `arranging/` at the plugin root, split by concern: reading the dump, the common rules, a front end per input, a file per right and left hand, the arranger's workflow and the main session's steps. A skill names the files it combines, and the dispatch prompt gives them to the arranger by absolute path. Before, `arrange-transcription` cited `arrange-cover`'s references section by section with exceptions, pinned by a test list of 27 cited names, and a third texture would have been a third mode with more exceptions, which the user refused. The directory sits at the plugin root because Claude Code scans `skills/` for `<name>/SKILL.md` folders and documents nothing else there.
- **`check-arrangement --melody` lists the vocal notes the right hand leaves out and never flags them.** A note may stay out on purpose, a stray of the transcription or a run too fast to read as it falls, so the agent adds each one or records why it stays out.
- **`check-arrangement --source` lists the left-hand notes the band's sustained parts don't back, and never flags them.** It was chosen over a reviewer agent: a reviewer reading the same dump with the same rules repeated the arranger's misreads, a bass fill read as a slash chord and a backing vocal's passing tone as a chord tone. The backing is the band piano's held notes, the bass in its home register and the marker in force. A held note lasts an eighth or more, so a sixteenth run or a sliver never backs; the home register runs up to B2, MIDI 47, an octave and a fifth above the open E string's E1 (28 + 19), where a standard-tuned bass's roots sit, so a fill or a line above it never backs. A `~` note is checked when nothing of the left hand sounds below it, since an invented walk-up is still a bass the band doesn't play. Each left-hand note a minor second or a minor ninth from a held band-piano note is listed too: counting every semitone by pitch class listed mostly the band's own colours, an octave or more apart, so only a minor second or ninth counts. The transcription and its markers are evidence, not the answer key, so a listed note is fixed or kept with its reason, never flagged. It is deterministic and runs no model.
- **`regrid` puts the bars back on the grid.** Every command counts bars from the cover's tempo map, and where the beat tracker miscounts a few bars, every later bar is numbered off. `regrid` turns each hiccup's tempo changes into one, moving the ticks and never a note's time. Its rule can't tell a hiccup from a tempo change that returns to tempo, so each span is checked by ear. A cover made on the [steady tempo grid](#the-steady-tempo-grid) needs none.

### The score

- **A text score, a bar at a time, on the sixteenth grid.** Each bar gives its chords, its pedal and up to three hand lines: the melody, the rest of the right hand and the left hand. Positions and durations count sixteenths on the cover's meter and tempo map, so bar N of the score sounds where bar N of the cover does.
- **Pop chord symbols with their own table, not Harte labels.** The agent writes the symbols as a chord chart spells them: flats, tensions in parentheses, slash basses, `N.C.`. `chords.py`'s Harte labels have no flats and no tensions. A quality the table lacks is written as the nearest one and recorded as a gap; the table can gain it.
- **The version is a header line,** `format 1`. `tests/test_skills.py` ties it to `arrangement.FORMAT_VERSION` in the skill and the docs, as it ties the spec version to `corrections.SPEC_VERSION`.
- **Repeats are copies with whole-bar overrides.** A copy takes its source as it stands at the copy line, and a `bar N` block replaces a copied bar whole: one rule, and a bar can be changed without touching the rest. Overrides per hand line were the alternative.
- **The pedal comes from the score:** per chord by default, a list of positions or none per bar. The build lifts and presses again where an attack would ring a semitone or a minor ninth against a note the pedal holds.
- **A pitch struck again in one hand cuts its earlier note short,** so a falling-notes view draws two notes.
- **The check builds in memory.** It takes the score and the cover, not a MIDI, so it checks exactly what the build plays.

### Playable arrangements

A falling-notes video reads as a piece someone could play, so an arrangement is written for two hands at an advanced level, and `pianoize check-arrangement` verifies that each hand can play it, unless it is a full arrangement (below), written for listening. The agent assigns the hands as it writes, rather than pianoize splitting the cover's one piano part as first planned. Every arrangement, and every correction, must keep the check passing, in its mode.

- **The limits** ([docs/arranging.md](arranging.md#checking)): at most 7 keys held in one hand, a span of at most a twelfth, no jump of a hand of 19 semitones in under 0.2 s, 26 in under 0.36 s or more than 36 at all, no crossed hands, the melody on top of the right hand, and no key struck twice at once. A span of 17 to 19 semitones, wider than a tenth, is listed but not flagged, so it can stay where the music needs it.
- **They were widened on 2026-10-15** from the first agent-written arrangement's (5 keys, a tenth, jumps of 15 semitones in 0.2 s, 22 in 0.36 s and 26 at all). On an instrumental with a full band, every note of the transcription on piano sounded better to the user than any reduction to those limits; the user chose wider numbers over a pedal-aware span count or an unplayable exception for the song. The full arrangement, below, came after.
- **A full arrangement drops the limits on the hands,** for listening rather than playing: `check-arrangement --full` skips the keys a hand holds, its span, its jumps and crossed hands. It still checks a key struck twice, now in either hand or both, the melody on top, now of both hands, and the harmony. Twice, on instrumentals with a full band, the user preferred every band part on piano to a reduction to two hands, the second time after the limits were widened. Every track of the transcription on piano was muddy, though, so a full arrangement keeps that fullness and leaves out what muddies it. An arrangement from a cover is playable unless the user asks for a full one, since the cover's accompaniment is already a pianist's; an instrumental's, from the transcription alone, is full unless the user asks for a playable one; and [the vocal arrangement](#the-vocal-arrangement) has a full right hand over a left hand checked playable on its own.
- **The harmony is checked too:** an accompaniment note outside the score's chord at its onset is flagged unless marked as a passing tone.
- **Every note gets one velocity, 88,** the M3 prototype's loudness-matched value. Most piano covers barely vary their dynamics, so pianoize writes none; loudness is `render --gain`'s.

### The transcription-only arrangement

tsumugi-piano-cover's weights are CC BY-NC 4.0, so a video made from its cover stays non-monetized ([Licenses](#licenses)). tsumugi's transcriber has MIT code and weights, and hololive's guidelines allow an individual's ad revenue ([What goes into a video](#what-goes-into-a-video)), so an arrangement made from the transcription alone would be monetizable. Where the grid was not applied, it also escapes a cover whose rhythm bends with a wrong tempo map, since the transcription's notes stay timed from the audio.

Its first trial, a clean-room arrangement of the first test song's opening that read no cover, never settled the left hand: the first version was too thin, the second too busy, the third still unsettled, and the user preferred the cover's arrangement. A band transcription has no pianistic accompaniment to keep the feel of, as a cover has, so the band has to be arranged for piano, which needs its own instructions.

Its second approach arranges the band layer by layer rather than as a pianist's accompaniment: a full arrangement that takes each band part in its own register, leaves out the transcription's errors and what muddies the parts together, and keeps one figure per layer through a section. It came from an instrumental arranged from the cover and the band, written to follow the band, which the user preferred full to playable. Run clean-room on a second instrumental, it sounded better to the user than an arrangement from the cover.

So `arrange-transcription` is a regular path, and the default for an instrumental. With no voice to carry, the cover's pianistic accompaniment matters less than the band's own parts, and the clean room keeps the result free of the cover's terms. A sung song has its own clean-room path, [the vocal arrangement](#the-vocal-arrangement). The path is the `arrange-transcription` skill, with its clean-room rule (no cover is read), its full arrangement by default and the shared rule files in `arranging/` it combines; `pianoize build-grid`, which builds the tempo-grid MIDI from the transcription; `dump-bars --drums`, which prints the drum lines, and which `arrange-cover` reads too now; and `dump-bars --every-note`, which prints every note of the band's parts for a full arrangement.

### The vocal arrangement

On a sung band song the user compared three arrangements: `arrange-cover`'s playable one, whose left hand won; `arrange-transcription`'s full one, whose right hand won, the melody an octave up with the backing vocal a third under it and the band piano's mid-register line; and a test that kept that right hand and rewrote the left hand as a pianist's accompaniment, which won outright and was approved once its harmony was fixed. So `arrange-vocal` is the default for a sung song, clean-room like the transcription-only arrangement, and `arrange-cover` runs when the user asks for it.

Its left hand follows `arranging/left-hand-accompaniment.md`: a bass on the strong beats and a two-note chord holding the third on the backbeat, the chord's root rather than every note the bass guitar plays, only what the band's sustained parts agree on, density rising through the song, and one figure per section. The band-layer left hand had laid a held pad under the bass guitar's rhythm on one low pitch, which lost; the test's remaining faults were all a chord root misread, a bass fill taken for a slash bass or a passing tone voiced as a chord tone, which the sustained-parts rule and `check-arrangement --source` address. The file replaces the unsettled left hand of the transcription-only arrangement's first trial, and `arrange-transcription`'s playable mode uses it too. The whole is checked with `--full`, and the left hand once more without it, so one hand can play it.

## Rendering

### MIDI is rendered with FluidSynth

[FluidSynth](https://github.com/FluidSynth/fluidsynth) renders MIDI to audio, run as a subprocess. It is installed with Homebrew, the one approved global install; the formulas it adds are recorded so they can be removed. The flags are fixed, `-R 0 -C 0 -r 44100` (no reverb, no chorus, 44.1 kHz) with a gain of 0.5 unless `--gain` sets one, so the same MIDI renders the same way.

The SoundFont is Salamander Grand Piano V3, for evaluation and for video audio. Every video description carries its credit line: "Piano sound: Salamander Grand Piano V3 by Alexander Holm (CC BY 3.0), via FreePats." Upright Piano KW (CC0 1.0, on the same FreePats page) is the fallback if the sound disappoints.

### The viewer and the video

- **One web page draws every frame** at a time `t`; it is previewed in a browser and captured for the MP4. The user wanted a preview and an MP4 to upload. Python drawing the MP4 beside a separate web preview would have meant two drawing codes to keep the same, and a web viewer screen-recorded by hand drifts in sync and quality. With one page, the preview and the video can't disagree.
- **The capture** uses playwright-core with the installed Chrome (`channel: "chrome"`), so no browser is downloaded, and pipes the PNG frames into ffmpeg. The Playwright MCP plugin is an agent tool for checking the page while developing; the CLI can't call it. pianoize serves the page on 127.0.0.1, because Chrome refuses ES modules from `file://`. Each frame is taken with Chrome's fast PNG encoder (`optimizeForSpeed`): the same pixels as a screenshot's, in about 60% of the time on frames full of glow, whose gradients compress slowly.
- **The look is lit, not flat.** The user asked for particles and something flashier than Synthesia's flat style, like the visualizers popular now (2026-10-15). The notes glow in their hand's colour; where a note meets its key a flare flashes at the note-on and glows while it sounds, a soft beam rises from the key, and sparks burst and then stream up. The roll darkens towards the top with a faint line up from each C, and the keys have the felt's shadow and the black keys' bevels. Green for the right hand and blue for the left stay, Synthesia's convention. The effects are drawn here, not taken from Neothesia, whose code is GPL. Every colour and every size of the frame is in `viewer/style.js`.
- **The effects' strengths are tried on the page and kept in `style.js`.** The page has a slider for each, but the render takes no option for them: the user chose to try levels with the sliders and then change `style.js`'s values, over a `--look` option or a look file passed to `render-video`.
- **The sparks are a function of the time alone.** Each one's randomness is a hash of its note's pitch and onset and its own number, so the preview, a seek and the capture draw the same frame, and two renders stay byte-identical. The effects start at the note-on and stay off the keys' bottom, so the sync test still reads the key's own light.
- **On screen** are the 88 keys, the notes falling coloured by hand, the pressed keys lit, and the title card. The user did not choose chord names, melody highlighting or a pedal display, so the arrangement JSON carries only the notes and their hands. Velocity is left out, since every note has one.
- **The timeline:** 1920×1080 at 60 fps, H.264 with AAC in MP4, and a fixed fall time of 3 s. The music starts at 3 s, one fall time, so the first notes have a full fall time to arrive. The title card lies over the roll while they fall in, with a shadow to keep it readable, and fades out as the music starts: the user wanted the notes sooner than after a title card and an empty keyboard. The video ends with the music: the user moved the credits from a closing card to the video's description.
- **The thumbnail comes with the video,** at the user's request, so one run makes the pictures an upload needs. It is the moment with the most notes on screen, zoomed in on them, the title card's lines over a dark band: the frame the user chose by eye, found by count.
- **The upload's text is the `make-video` skill's,** in `upload.md` beside the video: the title, the description with its credits and hashtags, and the tags, in English with a Korean translation, which YouTube shows by the viewer's language. The user wanted the metadata in one file, in both languages; it needs judgment per song, and the CLI never calls an LLM.
- **The audio is padded in Python** so that the WAV's clock is the video's: the preview plays it through an `<audio>` element, and ffmpeg muxes it with no offset.
- **BT.709.** ffmpeg converts RGB to YUV with the BT.709 matrix and tags the video BT.709; otherwise it would use BT.601 untagged, and players would shift the colours.
- **Sync.** A key lights on its note-on's frame. The Salamander piano's attack passes −40 dBFS about 20 ms later, within the sync test's one-frame tolerance.
- **Repeatability is promised for one Chrome and one ffmpeg.** Two renders of the same inputs give identical frames and MP4 bytes, but Chrome updates itself, so the frames can change between its versions.
- **Scratch files sit beside the MIDI and the output,** so the song's JSON and audio never leave `work/`.
- **npm keeps its default cache, `~/.npm`,** which npm manages and the user's other projects share. A cache under `work/` needed a relative path in `.npmrc`, which npm resolves against its working directory, not the file's.

### The viewer on GitHub Pages

The viewer also runs on GitHub Pages, playing an arrangement the user picks ([docs/rendering.md](rendering.md#on-github-pages)).

- **The input is the arrangement JSON and an audio file,** chosen over the arranged MIDI, which would need a MIDI reader in JavaScript beside `roll.export`, and over a saved preview run, which would need a new CLI option.
- **The arranging skills export the JSON** beside `arranged.wav` and point the user to the home page, so the plugin alone gets an arrangement there, with no checkout to run `export-arrangement` from. The user asked for it once the home page's steps showed that gap.
- **The audio is required:** the `<audio>` element stays the clock, chosen over a silent mode with a clock of its own.
- **One page.** `main.js` fetches `run/manifest.json` by a relative path, and a 404 makes it the home page. The capture's frames stay byte-identical, and the page works below `/pianoize/`.
- **It is the project's home page,** the user's "main entry point": a short introduction, the stage with the picker on its empty keyboard, the player, and the steps that make an arrangement. The user chose an empty keyboard over a silent demo loop, and the introduction above the stage over a full-width stage first. On a short window the stage narrows so that it and the player fit one screen, and a pick scrolls them into view with the focus on Play: a usability pass found the player below the fold on a laptop, with nothing on screen to press.
- **Its own player.** Play and pause, the time and a seek bar, a click on the picture, Space and the arrow keys replace the browser's audio control; the local preview uses the same player.
- **A file that fails its check replaces nothing.** The JSON is loaded and the audio's metadata read in a scratch element before either replaces what plays, and a MIDI is refused with a pointer to `export-arrangement`. While both files play, an error shows under the player, not over the stage.
- **The files stay in the browser.** They are read through blob URLs and sent nowhere, so the rule that audio never leaves the machine holds.
- **The JSON is checked.** `load()` refuses a file with no `notes` array or a pitch off the 88 keys. `export-arrangement` never writes one, but a picked file can, and one such note threw inside the animation frame and stopped the drawing for good.
- **No cards or lead-in.** The audio's 0 s is the music's 0 s, so the page draws the roll from 0 s, with no title card over it.
- **The page's colours, font and corner radius come from `style.js`,** through CSS custom properties that `main.js` sets, so the page and the video share one palette: the frame's background, the cards' text colour and font, the white keys' colour for the solid controls, the felt strip's for rules, and the notes' corner radius. Its layout sizes are in `style.css` and `controls.css`, and the CSS mixes tints of those colours with `color-mix()` for the muted text, the code backgrounds and a hover. The font is the cards' Helvetica Neue, with no web font, so the page loads nothing from elsewhere.
- **A GitHub Actions workflow deploys it,** since a branch deploy publishes only the root or `docs/`. It uploads only the page's files.
- **One picture for the link previews and the README:** `viewer/social.png`, the page's `og:image`, the README's hero and the repository's social preview. It is a frame the viewer draws, so it shows what pianoize renders, from made-up notes, since a frame of a song would be made from its recording. `viewer/social.mjs` draws it again from `social.html`, so it follows the look in `style.js`.
